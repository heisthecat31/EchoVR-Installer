# EchoVR Installer Changes

This file documents all the changes made to the EchoVR Installer application during the current chat session.

## Changes Made

### Theme and UI
- Forced the application to always use a dark theme to ensure button color consistency between light and dark modes. This was done by changing the parent theme in `app/src/main/res/values/themes.xml` and `app/src/main/res/values-night/themes.xml` to `Theme.MaterialComponents.NoActionBar`.
- Made the Discord link in the "New Player" and "Better Graphics" popups more prominent by changing the clickable `TextView` to a `Button`. This was done in `MainActivity.java`.

### Version Checker
- Added logging to the `isNewVersion` method in `InstallerManager.java` to help diagnose an issue where the app always reports an update is available. The logs will show the current and remote versions being compared.
- The `checkForUpdates` method in `InstallerManager.java` was already correctly implemented to fetch the latest release from GitHub and compare versions. No changes were made to the logic itself.

## Update Manifest Format (Quest asset patches)

Verified the `update.manifest` parsing/apply flow (`ManifestParser.java`, `UpdateManifest.java`, `UpdateManager.java`) against the documented format: header parsing (`Base URL`, `BASE_APK`, `Target`), `add`/`del` entries, local vs. remote asset path resolution, and the `add` match/mismatch-by-SHA256 logic were all already correct. Changes made:

- **Implemented BASE_APK mirror download** (previously missing): `UpdateManager` now resolves the manifest's `BASE_APK` name against the two documented mirrors (`https://files.echovr.de/`, then `https://evr.echo.taxi/` as fallback), verifies the SHA256 against the manifest's `BASE_APK` hash, and prompts to install it. Previously the app's base-APK URLs (`echoVrLegacyUrl`/`backupLegacyUrl`) were hardcoded via a separate `config.json` and had drifted out of sync with the manifest entirely (stale filename, wrong mirror order/priority, one using `http://`).
- When the installed base APK's marker hash no longer matches the manifest, `checkAndApplyUpdates` used to dead-end with an error telling the user to manually reinstall. It now surfaces a new `Listener.onBaseApkUpdateAvailable(manifest)` callback (only for the explicit "Check for Game Updates" action, not silent background checks) so `MainActivity` can prompt to download+install the correct APK via `UpdateManager.downloadAndInstallBaseApk`.
- Fixed `Target:` path resolution to always resolve against `Environment.getExternalStorageDirectory()` instead of relying on `/sdcard` existing as a symlink (the old `isAbsolute()` check meant the fallback branch was effectively dead code).
- `ManifestParser` now also requires `Target:` to be present (previously a missing `Target:` header caused a `NullPointerException` deep in `UpdateManager` instead of a clear error).
- Extracted the marker-file-writing and APK-install-intent logic (previously private methods in `InstallerManager`, duplicated for the new base-APK-update path) into shared static helpers on `FileUtil`: `writeInstallerMarker(...)` and `launchApkInstaller(...)`. `writeInstallerMarker`'s `patched` field is now computed by comparing `base_sha256`/`installed_sha256` (matching the documented marker format) rather than by `File` object identity.
- Verified the full change compiles (`gradlew compileDebugJavaWithJavac`).

### Follow-up 2: on-device testing fixes (detection lag, background installs, permissions, button color)

Diagnosed via live `adb logcat` against the connected Quest 3 rather than guessing:

- **Echo VR "not detected" after install**: `<queries>` already declared `com.readyatdawn.r15` (not a visibility-filtering issue). The actual cause: `onResume()` only did one fixed 2-second delayed recheck of `isPackageInstalled()`; PackageManager settling after the system installer closes isn't reliably that fast. Replaced with bounded polling (`MainActivity.pollInstallState()` - every 1.5s, up to 8 attempts / 12s, stops early once installed+verified) in [MainActivity.java](app/src/main/java/com/echovr/installer/MainActivity.java).
- **Automatic permission granting - not possible.** Android has no API for one app to grant another app's runtime permissions without root or Device Owner provisioning; this is a deliberate OS security boundary, not something implementable from a normal sideloaded APK. What's real: `showPermissionGuidance()` was already auto-deep-linking to Echo VR's App Info page on first install, but raced a Toast/Dialog against the `startActivity` navigation. Reordered to show the explanation dialog first, navigate on acknowledgement.
- **Background game data + patch install**: added [GameDataInstallService.java](app/src/main/java/com/echovr/installer/GameDataInstallService.java), a foreground service (type `dataSync`, progress notification) that runs `installGameData()` then `checkAndApplyUpdates(null, true)` in sequence, protected from process death while the app is backgrounded (e.g. during the APK install confirmation screen). Auto-started from `installLegacyEchoVr()` and `installCustomApk()` whenever `verifyDataInstallation()` is false, so it kicks off alongside the APK install instead of requiring a separate manual step. Added `FOREGROUND_SERVICE`/`FOREGROUND_SERVICE_DATA_SYNC` permissions and requests `POST_NOTIFICATIONS` at runtime on API 33+ (degrades gracefully - the service still runs without a visible notification if denied). Scope note: the existing manual "Download/Reinstall Game Data" buttons still call `InstallerManager` directly with the in-app progress dialog, unchanged - only the auto-triggered-during-APK-install path goes through the service.
- **"Update EchoVR" popup automatic**: this was already wired up in the previous round (silent checks fire `onBaseApkUpdateAvailable` too). Nothing to fix here - the device's marker just doesn't currently have a base-APK mismatch to trigger it, since the last install matched the manifest exactly.
- New `update_echovr_button_background.xml` (vivid blue gradient, `#2196F3` -> `#0D47A1`) so the persistent button reads as distinctly "there's an update" rather than blending in with the other action buttons.
- Verified `gradlew assembleDebug` succeeds and reinstalled on the connected Quest 3 via `adb install -r`. Could not confirm on-screen/runtime behavior this round - the headset's VR shell deferred the launch ("Launch is blocked because: device in VRUI"), so `MainActivity` never actually resumed during the adb-driven check.

### Follow-up 3: stop nagging New Player / custom installs to "update"

Bug found via live testing: after installing through "New Player" (a user-supplied, already license-patched URL), the app started automatically offering to "Update EchoVR" - which would have replaced the working patched APK with the vanilla manifest APK. Root cause: `startApkDownload()`'s marker write recorded `base_sha256` as the hash of the patched APK itself, which can never equal the manifest's vanilla `BASE_APK` hash - so every custom install looked like a "mismatch" once the previous round made that check run automatically.

Fix: added an `install_source` field to the marker (`FileUtil.writeInstallerMarker`, now `manifest` vs `custom`). `UpdateManager.checkAndApplyUpdates` now only compares `base_sha256` against the manifest - and only offers the reinstall popup - when `install_source=manifest` (i.e. actually came from the update manifest's `BASE_APK`/mirrors, via `installLegacyEchoVr()` or an accepted "Update EchoVR" offer). New Player, Enhanced Graphics, and Better Graphics installs are marked `custom` since we have no way to know what those user-supplied URLs actually correspond to - for those, patches still apply best-effort, but the base APK is never second-guessed. A marker with no `install_source` at all (written by a pre-fix build, like the one already on the test Quest 3) is treated the same as `custom`, so this self-heals without needing a reinstall.

### Follow-up 4: remove redundant button, fix polling being cancelled before it could ever fire

- **Removed `updateEchoVrButton`** (the persistent "at the bottom" button added two rounds ago) per feedback - it was redundant now that the popup fires automatically, and it never rendered blue since it lacked the `app:backgroundTint="@null"` that `viewLobbyLinkButton` already needed for the same reason (`Theme.MaterialComponents` applies a default tint to plain `<Button>`s that overrides/flattens a custom gradient `android:background` unless explicitly nulled out). Deleted `update_echovr_button_background.xml` and the now-dead `pendingBaseApkManifest` field along with it.
- **Fixed the detection-polling fix from two rounds ago - it could never actually fire.** `onPause()` was cancelling the scheduled poll, and the earlier logcat trace showed the Activity cycling pause/resume repeatedly during the install flow (focus bouncing between the installer, the system installer, and Echo VR itself) - every pause wiped the poll before its 1.5s delay elapsed, and every resume reset the attempt counter back to 0. If the app never sat still for one clean 1.5s stretch, it could go 30+ seconds without the poll firing even once - matching exactly why only a later, separate trigger (reopening the app, clearing cache - both just call `checkState()` once, coincidentally after enough real time had passed for PackageManager to settle) appeared to "fix" it. Now: polling is no longer cancelled on pause (continues in the background regardless of visibility - safe, `checkState()` just sets view properties), a `pollingActive` flag stops repeated resumes from resetting the counter mid-run, and the window is extended from 12s to 30s (20 attempts) for headroom. Only cancelled in `onDestroy()`.

### Follow-up 5: mod patches silently skipped after a background game-data install

Bug: `GameDataInstallService` runs the game-data download concurrently with the base-APK install (that's the whole point - overlap them), but the marker file `checkAndApplyUpdates` needs is only written once the APK download finishes. The ~894MB data download can easily finish first, especially since the APK install also needs a human tap to confirm. When that happens, the one-shot silent `checkAndApplyUpdates(null, true)` call finds no marker yet and no-ops with no callback at all (correct behavior for its normal caller, wrong here) - and the service only had a single 60s timeout that gave up rather than retrying, so mod patches never got applied. Fixed in [GameDataInstallService.java](app/src/main/java/com/echovr/installer/GameDataInstallService.java): `attemptPatchCheck()` now retries every 10s for up to 5 minutes total, cancelled early the moment a real success/error callback arrives.

### Follow-up 6: corrected which step runs in the background - patches, not game data

Misread the original request: I had `GameDataInstallService` auto-download the ~894MB game data zip in the background whenever an APK install started. That was wrong - game data was always meant to stay a normal, manual, foreground action (the "Download Game Data" button, unchanged). It's the smaller mod-patch check *after* data finishes that needed to survive the user switching away (e.g. to confirm the base APK's system install dialog).

- Renamed/reworked `GameDataInstallService` -> [ModPatchService.java](app/src/main/java/com/echovr/installer/ModPatchService.java): now only runs `checkAndApplyUpdates`, with the same retry-until-marker-exists logic from the last round. No longer touches `InstallerManager`/game data at all.
- Removed the auto-trigger from `installLegacyEchoVr()`/`installCustomApk()` entirely - game data goes back to being purely user-initiated.
- `InstallerManager.installGameData()` now starts `ModPatchService` itself right after `verifyDataInstallation()` succeeds, so the patch check kicks off at the actual source of "data is ready" rather than depending on `MainActivity` noticing on its next resume.
- `MainActivity.checkState()`'s existing silent auto-check (for a returning user who already has data) now also routes through `ModPatchService` instead of calling `UpdateManager` directly, so there's one consistent, resilient code path for every "opportunistic background patch check," while the explicit "CHECK MOD UPDATES" button stays as a direct Activity-driven call with its normal progress dialog.

### Follow-up 7: patches should run concurrently with game data, not after it

Still had this sequenced wrong: `ModPatchService` was triggered from `installGameData()`'s *success* callback, so patches only started once the whole ~894MB download+extraction finished. Moved the trigger to the top of `installGameData()` instead, so it fires the moment the download starts. Patches don't actually depend on game data being present at all - they're separate files under `Target`, the only real dependency is the base APK - so there was never a reason to make them wait in line.

### Follow-up 8: security review fixes (del-entry parsing; signing key flagged, not yet rotated)

- Fixed `ManifestParser.parseEntry()`: it required 3 whitespace-separated parts for every entry, so a `del <path>` line with no trailing hash was silently dropped. `add` still requires a hash (needed to verify the download); `del` now accepts either 2 or 3 parts, matching the spec ("del — delete the file") which never required a hash for it. No live manifest entries were affected yet since the current manifest has no `del` lines.
- **Signing key: removed entirely** (Better Graphics patching was already dead/unreachable - no button called it anymore). Deleted `ApkPatcher.java`, the tracked `key.p12` keystore, `key.p12.bak`, `DumpKey.java` (the local-only script - not in the public repo - that had extracted the key and still had its password), `InstallerManager.installBetterGraphics()`, `MainActivity.showBetterGraphicsDialog()`, the now-unused `com.github.iyxan23:zipalign-java`/`com.github.MuntashirAkon:apksig-android` dependencies, and the JitPack repository they needed. The exposure still exists in git history on `github.com/heisthecat31/EchoVR-Installer` (removing files from the working tree doesn't erase prior commits) - full remediation of that would mean history-rewriting on a public repo with existing forks/PRs, which needs its own explicit decision if wanted later.

### Follow-up 8 (2026-10-15): Discord sign-in stuck on "loading" forever

Picked this project back up after a gap - found `DiscordAuth.java` already added in the meantime (OAuth2 via the device browser + a loopback HTTP callback server on 127.0.0.1:53124, ported from the EchoVR_Launcher desktop app's pattern), not something from an earlier session here.

Diagnosed live on a connected phone (screenshots + adb), not guessed: tapping "Authorise" in Discord left the app stuck on "Opening Discord in your browser..." indefinitely. `cat /proc/net/tcp` showed the browser's connection attempts to port 53124 stuck in `SYN_SENT` - never established, never refused - while logcat showed Samsung's "Freecess" freezing our process's background threads within seconds of opening the browser (`FreecessController: FZ`, `ActivityManager: freezing ...`). Once frozen, the app can't complete the TCP handshake for Discord's redirect back to it, so the local server just sits there forever no matter how long you wait - this is Android/Samsung's battery-optimization background-freezing, not a Discord, redirect-URI, or server config issue.

Same root cause this project already hit once with `ModPatchService`: a backgrounded app with no foreground component gets frozen. Fixed the same way - added [DiscordAuthKeepAliveService.java](app/src/main/java/com/echovr/installer/DiscordAuthKeepAliveService.java), a foreground service with no logic of its own that just brackets `DiscordAuth.start()`/the terminal callbacks (`onPatchUrl`/`onError`)/cancel/`onDestroy`, purely to keep the process unfrozen while waiting for the browser redirect. Reran the exact same flow after the fix: connection completed, exchange request reached the server and got a real response back (403) instead of hanging - confirmed fixed.

Separately, that 403 response itself ("must join the Echo VR Patcher server first") is `files.echovr.de`'s own bot/API business logic, unrelated to this bug and outside this project entirely. Turned out to be user-side in this case too - wrong Discord account signed in (confirmed via the exact server response, logged by a small addition to `DiscordAuth.exchange()`: `Log.i(TAG, "Exchange returned status " + status + ", body: " + body)` - kept in place since it's cheap and will save a round-trip next time an auth error needs diagnosing).

Also checked a reference project for this same bot/community (github.com/Crafter-1/Quest-EchoVR-Installer, a Unity in-headset app) to see how it handles Discord: it doesn't do in-app OAuth at all - the user gets their patch link from the bot inside Discord itself, then pastes it into the app (clipboard-paste button + URL extraction from the pasted text). This app already has that exact fallback ("I already have an APK link"); decided to keep automatic sign-in as the primary flow for now and revisit only if the freezing-class of bug resurfaces.

### Follow-up: manifest-driven Legacy install + automatic update checks

- **`installLegacyEchoVr()` now resolves the base APK from the update manifest** instead of `config.json`'s `legacyUrl`/`backupLegacyUrl` (confirmed live those two fields are stale — `16-07-2026` vs. the manifest's current `27-08-2026`). It fetches the manifest, tries `UpdateManifest.APK_MIRRORS` in order (reusing the existing resumable `downloadFile` engine for progress reporting), and verifies SHA256 before installing. Removed `echoVrLegacyUrl`/`backupLegacyUrl` from `InstallerManager` and their `config.json` parsing entirely, since nothing reads them anymore. `dataUrl`/`enhancedUrl` (and their backups) are untouched — the manifest has no equivalent for the game-data zip or the Enhanced Graphics APK. The hosted `config.json` itself still has the two now-unused keys; harmless to leave, safe to drop whenever it's next edited.
- **Installer self-update check is now automatic**: `InstallerManager.checkForUpdates` gained a `silent` overload; `MainActivity.onCreate` calls it once on startup. Silent mode stays quiet unless an update is actually found (no progress UI, no "no updates" toast) - the manual "CHECK UPDATES" buttons still work as before for an explicit re-check.
- **Echo VR game update check is now automatic too**: `UpdateManager.checkAndApplyUpdates`'s base-APK-mismatch branch used to only notify on an explicit "Check for Game Updates" tap (silent background checks just returned quietly). It now notifies either way, so the first automatic check after launch can surface it without the user asking.
- **New "Update EchoVR" popup**: renamed/rebuilt the confirmation dialog with a "what's new" summary built from the manifest's entries (count of files to add/update vs. remove, plus the new build's filename) - the manifest format has no free-text changelog field, so this is a structural summary rather than prose patch notes.
- **Persistent fallback button**: added `updateEchoVrButton` to `activity_main.xml` (hidden by default). Declining the popup leaves the button visible at the bottom of the main screen so the offer isn't lost until the next full app restart; tapping it re-shows the same dialog. It's cleared/hidden as soon as the user commits to the download (tapping DOWNLOAD & INSTALL), since the marker file is written optimistically at that point same as every other install flow in this app.
- Verified the full change compiles (`gradlew compileDebugJavaWithJavac`).
